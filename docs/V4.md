# V4 — the agreed design for round 3

Agreed with the owner on 2026-10-11. Tasks T14 onward build this. Where it differs from `SPEC.md`, this file wins. Read only the sections your task lists.

## 1. What changes and why

The app stops trying to be an exploration tool. Exploring happens in Google Flights and Google Maps. The app collects what was found, lines up dates and prices, and helps narrow down. **Pasting a link must do the data entry**: a pasted flight creates the destinations, dates and price without the user typing them.

Workflow and tab order: **Overview → Routes → Map → Days**.

| Tab | Job |
|---|---|
| Overview | Trip window, travelers and home airports, chosen route summary, budget, album link, trip comments |
| Routes | Flight ideas as a hierarchy (§4) |
| Map | Places and stays together, per stop (§6, §7) |
| Days | Assign places to days on a map (§8) |

Removed: the Recap tab and public recap page, destination idea cards (candidates), voting on stays and candidates, the single trip "destination".

## 2. Look and feel

The approved reference is `docs/mock/routes-mock.html`. Its `<style>` block is the token source.

- **Tokens** (light and dark values are in the mock's `:root` blocks): `--bg --surface --sunk --line --ink --muted --teal --teal-soft --on-teal --sun --sun-soft --good --bad`. Add spacing tokens `--space-1..7` (4, 8, 12, 16, 24, 32, 48 px) and `--r: 16px`.
- **Dark mode** follows the phone or computer setting (`prefers-color-scheme`). No toggle.
- **Type**: Bricolage Grotesque (headings, 600/700), Instrument Sans (body, 400/500/600), JetBrains Mono (airport codes, prices, dates in columns; tabular numbers). One Google Fonts link.
- **Navigation**: under 760 px, a fixed bottom tab bar with icon and label (as in the mock) and a slim top bar with logo, trip name, Help and account menu. From 760 px, tabs sit in the top bar and the bottom bar is hidden.
- **Components to carry over from the mock**: segmented control, chip, `.btn` (plain, primary, quiet, small), kind pill, badge, option card, the rail (stops as dots, flights as inset blocks), toast.
- Teal is the action color. Sun is for small highlights only (cheapest, stale price, warnings). Semantic good/bad is only for price movement and errors.
- Tap targets 44 px. Visible focus ring. Respect `prefers-reduced-motion`.
- Category colors stay as they are (`js/lib/categories.js`).

## 3. App shell, hosting, sign-in

Mirrors the owner's Fight Club app, which behaves correctly on iPhone.

- **Hosting**: Firebase Hosting at `https://trip-planner-mattchurchman.web.app`, deployed by GitHub Actions on push to `master` after tests pass. `firebase.json` serves the repo root and ignores docs, tests, markdown and config files. No service worker.
- **Home screen app**: `manifest.webmanifest` (`display: standalone`, name "Trip Planner", icons in `img/icons/`), plus in every HTML page: `viewport-fit=cover`, `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, `apple-mobile-web-app-title`, `apple-touch-icon` → `img/icons/icon-180.png`. Fixed bars pad with `env(safe-area-inset-*)`.
- **Sign-in**: `authDomain` becomes `trip-planner-mattchurchman.web.app` (same site as the app, which is what makes iPhone sign-in stick). Google uses `signInWithRedirect` on phones and in the home-screen app, `signInWithPopup` on desktop. Email and password is offered beside it: sign in, create account, forgot password, with `autocomplete` set so iPhone offers Face ID fill.
- **Access** is still the `allowlist` collection. Rules keep `email_verified == true`, so a new password account gets a one-time confirmation email and a "Check your email, then tap Continue" screen. Google accounts are already verified.
- Per-trip membership (different groups per trip) is future work, not this round.

## 4. Routes

### 4.1 Hierarchy

```
Trip window
└─ Idea            e.g. "Rome round trip", "London in, Madrid out"
   ├─ Flights from home, per traveler (each traveler's own dates and prices)
   └─ Option       e.g. "Florence + Barcelona"
      └─ Hops      flights inside the region, shared by everyone, priced per person
```

Stops (where you sleep, and how many nights) are **never typed**. They are worked out from the flights.

### 4.2 Data

New subcollections under `trips/{tripId}/`:

```
ideas/{id}:    name: string, nameEdited: boolean, order: number
options/{id}:  ideaId: string, name: string, nameEdited: boolean, order: number
```

`flights/{id}` keeps every existing field and gains:

```
role: "home" | "hop"          // missing = a flight from before V4 ("earlier flight")
ideaId: string | null
optionId: string | null       // hops only
travelerId: string | null     // home flights only; hops are shared
direction: "both" | "out" | "back" | null   // home flights only: both ways, to the region, or back home
landsDate: string | null      // home flights going out: the date you land, "YYYY-MM-DD"
picked: boolean               // home flights only: counts toward this traveler's total
```

`trips/{tripId}` gains `chosenOptionId: string | null`. It stops using `destination`, `destinationId`, `selectedFlights` and `actualSpendCents` (leave old values alone; don't write them).

### 4.3 Airports

`js/data/airports.json` maps IATA code → `{ city, country, lat, lng }` for airports with scheduled service (source: OurAirports, public domain). `js/lib/airports.js` loads it once on demand and exposes `airportInfo(code)` and `cityKey(code)` (`"Rome, IT"`; FCO and CIA share a key). Unknown codes fall back to the code itself.

### 4.4 Rules (`js/lib/route.js`, pure, tested)

- **Movements**: flatten an option's hop flights into legs `{ from, to, date }`, sorted by date. A round-trip hop is simply two legs.
- **Stops** for one traveler: start at the city where their picked outbound home flight lands, on its `landsDate` (or its departure date if unset). For each movement, close the current stop on the movement date and open the next one in the destination city. The last stop ends on the date of their picked flight home. Nights = days between.
- With no home flight yet, start from the first movement and show the first stop with no start date.
- **Warnings** (shown on the stop they belong to): the next flight leaves from a different city than the one you're in; dates run backwards; the flight home leaves from a different city than the last stop; a flight has no date.
- **Total per traveler** = latest price of each picked home flight + latest price of every hop in the option. If any is missing a price, show the total as "at least $X".
- **Names** (until the user edits them): idea = "Rome round trip" when in and out cities match, else "London in, Madrid out". Option = hop cities other than the arrival city joined with " + ", or "Stay in Rome" with no hops.
- **Landing date guess**: if the destination is more than 60° of longitude east of the origin, default `landsDate` to the day after departure; otherwise the same day. Always editable.

### 4.5 Pasting a flight (the main data entry)

One **Paste flight link** action on the Routes tab.

1. Read the clipboard (`navigator.clipboard.readText()`; iPhone shows its own Paste bubble). If that fails or is refused, show a text box to paste into.
2. Parse with the existing `parseFlightLink`. A short share link shows the existing "copy the address bar" message.
3. Decide what it is, for the traveler currently selected:
   - Any leg starts or ends at their home airport or home city → **home flight**. If an idea with the same in and out cities exists, add it there; otherwise create the idea.
   - Otherwise → **hop**, added to the open option of the current idea (create "Option 1" if the idea has none).
   - If the traveler has no home airport and there are no ideas yet, treat it as a home flight and save its origin as their home airport.
4. Show one confirmation sheet with what was read (route, dates, airline, price) and where it will go, with a way to change the idea or option. One tap on **Add** saves it.
5. The first home flight in a direction is `picked`; later alternatives are not, until the user picks them.

Editing a flight by hand stays available (existing flight dialog) but is the fallback, not the path.

### 4.6 Screen

Match the mock: traveler switch, idea switch, the home-flights card, option cards with total, path line, badges (Chosen, Cheapest), and the rail. Differences from the mock:

- **No "Recheck" text link.** The price is the control (§5).
- Home flights list every alternative for the selected traveler, cheapest first, with a **Use this** / **Using** control.
- **Choose this option** sets `chosenOptionId`. Map and Days read their stops from it.
- Earlier flights (no `role`) appear in a collapsed "Earlier flights" list with **Move to…** (pick idea or option) and Delete.
- Travelers may have different dates. Stops and totals always show for the selected traveler.

## 5. Checking prices

Prices are a snapshot: the Google Flights link carries the price Google showed when the link was copied. The app never fetches prices.

- The price on a flight or stay is a button. A small age label sits beside it ("3d"), with a sun-colored dot once it is older than 3 days.
- Tapping it opens the saved link in a new tab and reveals one row: **Still $64?** with **Same** and **Changed**. Same logs a new price entry at the same amount. Changed shows a number field and Save.
- After a check, show the movement in words and color ("▼ $12 lower", "▲ $20 higher", "No change").
- **Check prices** on an option (and on the stays list) walks through every price older than 3 days, one at a time, in screen order.
- No link saved → skip opening, still ask.
- Price history and delete stay as they are, behind the existing History disclosure.

## 6. Places

- **Love / Like / Pass** replaces Must / Nice / Skip, on places only. Stored in the same `votes` map as `"love" | "like" | "pass"`; read old values as must→love, nice→like, skip→pass. One tap sets your pick, tapping it again clears it. Each person's pick shows as their initial. Sort: most Loves, then most Likes, Pass-only last. On the map, Loved pins are larger with a ring and Pass-only pins are dimmed.
- `places/{id}` gains `stopKey: string | null` (nearest route city within 150 km, set on save; `null` shows under "Elsewhere") and `layer: string` (the My Maps layer it came from, or "").
- Places no longer filter by `destinationId`. `recap` is unused.
- **Import from Google My Maps**: the user exports KML from My Maps (with "Export as KML instead of KMZ" ticked) and picks the file. The app reads layers and pins, shows a per-layer summary where each layer gets a category, skips pins that match an existing place (same name and within 50 m), and adds the rest. KMZ files get a message explaining the tick box.
- Adding one place by pasting a Google Maps link, by search, or by tapping the map stays.

## 7. Stays

- A stay belongs to a stop: `stays/{id}` gains `stopKey: string | null` and `out: boolean`. Votes on stays are no longer shown.
- Adding a stay from a stop pre-fills check-in and check-out with that stop's dates. **Duplicate** copies a stay so only dates and price need changing (for split stays).
- Status per stay: shortlisted (default), **Out** (dimmed, sorted last), **Chosen** (existing `selectedStayIds`).
- **Night coverage** per stop: a bar with one cell per night showing covered, not covered, or double-booked by the chosen stays, plus the chosen total and per-person share.
- Stay links still fill provider, dates, guests and sometimes the name. The price is typed.

## 8. Map and Days

- **Map tab**: one Leaflet map with place pins and stay price pins together. Stop chips across the top (All, then each city of the chosen option in order, then Elsewhere) filter both. Below the map (beside it from 760 px) a Places / Stays switch changes the list. With no chosen option, chips list every city across all options and a hint says to choose an option on Routes.
- **Days tab**: **Create days from route** makes one day per date of the chosen option, titled with that date's city. The map shows that city's places; tapping a pin offers the days to put it on. Pins are numbered and colored by day. The existing list controls and walking-route links stay.
- **Take it to Google Maps**: export one KML with a layer per day, a "Stays" layer for chosen stays, and a "Not planned" layer. The help text explains importing it into My Maps and opening it in the Google Maps app.

## 9. Overview

Trip name and window dates; travelers with home city and airport; chosen route as a one-line path with the selected traveler's total; budget (flights for each traveler, chosen stays, shared costs, per-person total); album link; trip comments. The shared costs list moves here from the old Flights & stays tab.

## 10. Help

`help.html` is rewritten as short text sections in workflow order: add to home screen and sign in, Routes (copying the right Google Flights link, pasting, options), checking prices, Map (My Maps import, stays), Days, taking the plan to Google Maps. Images and GIFs come in a later round; leave a marked placeholder comment where each will go.
